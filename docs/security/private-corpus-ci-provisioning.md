# Secure private-corpus CI provisioning (not yet enabled)

This package contains no merchant PDFs, cloud resources, credentials, or Product waiver. It does not change the canonical or Gold validators. The production package digest, object identity and generation in `config/private-corpus-ci-pins.json` are intentionally `null`; relevant PRs must fail until Product approves a real package and an operator completes the setup below.

## Trust boundary

The public repository's ordinary PR code receives no corpus. `.github/workflows/ci.yml` calls `.github/workflows/private-corpus-trusted.yml` by immutable commit SHA. During bootstrap, the called workflow checks out its security scripts and pins from the previously Product-accepted immutable commit `f7a3e83371af2ae5ecd275f60c4e284e549f7277` and verifies literal SHA-256 digests before running them. Neither mutable `main` (which does not yet contain this package) nor the PR checkout is the security-tool authority. Its unprivileged classifier reads the authoritative GitHub event and live GitHub API, rejects forks/stale heads, compares file paths against the existing policy's sensitive-file scope, and requires a matching owner-managed approval for any relevant change. A relevant authorized run alone enters the `ratereveal-private-corpus` environment. The secure job rechecks approval, checks out and verifies the exact code SHA, installs dependencies before corpus access, then obtains short-lived object-read access.

The trusted workflow also has a branch-limited, unprivileged synthetic runtime canary for `codex/secure-ci-corpus-provisioning`. It rechecks the live PR, verifies an exact-head checkout without persisting credentials, and requires the real download implementation to reject the deliberately unconfigured package identity before any OIDC or cloud request. This canary never substitutes for the `secure` job on a corpus-relevant change. Its lack of an environment and `id-token: write` is intentional.

The cloud federation rule must require the **numeric** repository ID `1176226912`, owner ID `198274179`, environment `ratereveal-private-corpus`, and `job_workflow_ref`/`job_workflow_sha` of the approved immutable called workflow commit. Do not grant access on repository name or environment name alone. Require GitHub OIDC issuer and the exact provider audience. Restrict the identity to the one approved package object/version using a read-only `storage.objects.get`-equivalent grant; no list, write, delete, or bucket administration. GitHub's protected environment is a second boundary, not a substitute for cloud-side workflow identity. Review trust-condition support with the selected provider before any corpus upload.

## Required owner/operator setup, only after Product separately authorizes it

1. Select the provider, project/account, region, privacy/data-processing terms, retention, audit, backup/recovery policy, and cost limit. Google Cloud Storage is a candidate, **not yet an approved storage destination**. Do not use GitHub repository storage, Actions artifacts or cache for the corpus.
2. Assemble the minimal uncompressed POSIX ustar package containing exactly eight approved PDFs under `documents/`, `gold-private-manifest.json`, `private-fiserv-restaurant-count-001.json`, and `product-source-provenance.json`. Do not include decision copies, unrelated merchant files, evidence archives, SQLite files, secrets, or rendered output. Preserve the exact approved manifest/provenance/document bytes and verify them offline. The archive must have regular-file entries only, no directory, link, extended-header, or special entries; each file is at most 128 MiB and the package at most 512 MiB.
3. Have Product approve the resulting package version, SHA-256, content-addressed object name, and immutable generation. Change only the `package` fields of the protected pin file through reviewed Git. The pre-existing Gold/canonical/provenance and G1–G8 SHA-256 pins must not be rewritten for convenience. The validator rejects a manifest-plus-PDF replacement against those independent pins.
4. After separate authorization, upload the package to an encrypted versioned/immutable private object store with access auditing and a recovery copy. Give the CI identity read access only to the approved object/version; disable public access. Keep Product provenance records in owner-controlled retention, separate from PR artifacts. Confirm the object generation and package hash before permitting CI access.
5. Create GitHub environment `ratereveal-private-corpus` in repository settings. Require Product/security reviewers, enable **prevent self-review**, disable admin bypass, and verify that the repository plan supports those protection rules. Do not populate repository-level secrets with the environment secret names below. Never approve a job until its displayed repository/base/head SHA and package version match Product's decision. A missing environment secret makes the secure job fail closed, but reviewers must also audit the environment protection settings; the job's read-only token cannot administer or attest to them.
6. Configure the **repository variable** `RATEREVEAL_PRIVATE_CI_APPROVAL` as JSON with numeric `repositoryId`, `eventName` (`pull_request` or `push`), 40-character `baseSha`, 40-character `headSha`, and `packageVersion`. It is an authorization record, not a secret; repository administrators must update it for each approved exact SHA. A changed PR head or base needs a new approval. A post-merge push SHA likewise needs its own approval if the change is corpus-sensitive.
7. Configure these **environment secrets**, which hold non-secret configuration but are released only after review: `RATEREVEAL_TRUSTED_WORKFLOW_SHA` (the called workflow's immutable commit), `RATEREVEAL_GCP_WIF_AUDIENCE` (full provider resource), and `RATEREVEAL_GCP_BUCKET`. Do not create service-account keys. The code deliberately rejects missing values. Configure a provider-side workload identity federation condition and narrow storage IAM grant matching the called workflow SHA and numeric repository/owner IDs. Set `RATEREVEAL_PRIVATE_CORPUS_WAIVER_ID` and `RATEREVEAL_PRIVATE_CORPUS_WAIVER_SHA` nowhere in the normal path.
8. **Do not configure the real corpus or treat this package as a merge control yet.** The current user-owned repository ruleset requires `private-corpus-policy` from the GitHub Actions app, while the reusable workflow reports `private-corpus-policy / private-corpus-policy`. More importantly, GitHub's name-plus-app required-check identity cannot distinguish the intended reusable workflow from a same-named PR-authored Actions job. Owner review is useful but is not cryptographic check attribution. Before real access, Product must approve a genuinely independent merge attester (for example, a separately controlled GitHub App that verifies exact trusted-run provenance before publishing its own required check) or a platform migration that supports required workflows outside PR control. Preserve existing rules until a stronger replacement is reviewed; a check-name change alone is insufficient.

The environment does not yet exist in this package. GitHub can auto-create an unprotected environment when a workflow references a missing name. This implementation therefore also requires environment-scoped configuration and a Product exact-SHA record; without them it cannot request or use cloud access. The operator must verify reviewer/bypass settings out of band before a real canary. Do not interpret a green local synthetic test as proof of GitHub/cloud configuration.

## Validation and logs

The trusted job downloads into `$RUNNER_TEMP/ratereveal-private-corpus.tar` and hashes the whole archive before parsing. It rejects unsafe ustar entries, unexpected/missing files, duplicate cases, G9 inclusion, altered manifests, and altered documents. It extracts only verified regular files with restricted permissions into `$RUNNER_TEMP/ratereveal-private-corpus`, outside `$GITHUB_WORKSPACE`. The `RATEREVEAL_PRIVATE_CORPUS_DIR` variable exists only on the validation step. Validator output is captured in memory and reduced to status/counts; no raw PDF text, filenames, archive contents, or cloud tokens are logged. No secure job uses cache or `upload-artifact`. The always-run cleanup removes the precise package, corpus, and SQLite/WAL/SHM paths; GitHub-hosted VM teardown is a second boundary, not a guarantee of physical secure erasure after an infrastructure crash.

Run local synthetic tests with `node --test test/private-corpus-ci-security.test.mjs`. Before real access, run a GitHub synthetic canary proving fork/unapproved/stale/identity failures, missing configuration, and cleanup. Vercel preview creation for the security-only staging branch is disabled by the exact-branch `git.deploymentEnabled` setting in `vercel.json`; other preview branches and production remain unchanged. Only after Product/provider approval should an operator enable the real package pins and environment, then run one exact-head real canary and inspect logs, artifact/cache inventory, cloud access audit, canonical/Gold results, and private-corpus-policy status. Do not push or create a PR from this package without separate Product Git authorization.

## Rotation and recovery

Any package or source-pin rotation is a Product source-authority decision, not an automatic CI change. A protected workflow/script edit requires a new pinned workflow commit, updated literal script digests, cloud trust update, and caller pin update. Revoke the old cloud binding once the new canary passes. If a run fails or a package is unavailable, do not waive the gate; restore the approved immutable object/version from owner-controlled backup or stop integration.
